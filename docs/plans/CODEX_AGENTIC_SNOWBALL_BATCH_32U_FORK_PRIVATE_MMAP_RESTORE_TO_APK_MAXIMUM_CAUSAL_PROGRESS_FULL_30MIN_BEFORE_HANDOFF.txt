OPENING DEFECT — PRIVATE FILE BACKING ACROSS FORK/CHILD EXEC/PARENT RESTORE

Current file-backed mappings use external_private_file_backing and external_next_private_file_backing.

The existing fork-shaped clone path snapshots parent process state but was designed before this second backing class existed. Review found that parent restoration can therefore rebuild runtime mappings using the old prepared backing class or bytes after a child exec has reset/reused the private-file pool.

This can leave a dynamically linked parent with apparently valid mapping topology but corrupted shared-library bytes after child execution.

OPENING REPAIR REQUIREMENTS

1. Trace the existing clone snapshot, child execution, termination, and parent restoration path completely before editing.
2. Represent enough backing identity to distinguish at least:
   - ordinary prepared/image runtime backing;
   - private file-mapping backing.
3. Preserve the parent's private-file backing bytes and allocation cursor across the supported fork-shaped clone lifecycle.
4. Child exec/reset must not destroy the state required to restore the parent.
5. Parent restoration must map each runtime-owned mapping from its original backing class rather than assuming one backing array.
6. Preserve existing process/descriptor/pipe/cwd snapshots and ownership behavior.
7. Preserve PREPARE -> COMMIT, rollback/failure atomicity, W+X=0, SUM clear, bounded resources, and parent-shell liveness.
8. No apk/libcrypto/path/fd special cases.

PERMANENT PROOF

Add the smallest focused permanent regression that proves the process-state contract rather than only helper behavior.

- parent owns a file-backed private mapping with known bytes;
- fork-shaped clone snapshots parent state;
- child execution mutates/resets/reuses its own runtime/private backing state;
